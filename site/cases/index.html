Cases

Two use cases: the situation, what Flid does, what changes and what it runs on.

Engineering master data from CAD and ERP

Situation
A manufacturer with CAD and ERP data. Parts, drawings and assemblies live in the vault; item numbers, stock and transactions live in the ERP. Answering “where is this part used, and does the drawing match the ERP?” means opening several systems.
What Flid does
A four-week Alloy Catalog pilot reads the vault database read-only, matches files to the ERP item master, and publishes one page per part with bill of materials, where-used, drawings, stock and data quality checks.
What changes
Engineering, purchasing and service search one catalog and ask the assistant, which cites the files and records it used. Conflicts between CAD and ERP are listed for clean-up.
Runs on
Alloy Catalog, the vault database (read-only), the existing ERP.

Governed metrics as code

Situation
A data team whose dashboards each define revenue and margin slightly differently, with access rules kept by hand per report.
What Flid does
Moves connections, models, metrics and dashboards into YAML in Git with LeapView, validated before publishing, with row filters and column masks applied in one place. LeapView is an alpha, so this starts as an evaluation.
What changes
One definition per metric, used by dashboards, headless queries and AI tools. Changes go through review like code.
Runs on
LeapView, DuckDB and PostgreSQL on the team’s own infrastructure.
